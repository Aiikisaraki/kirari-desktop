# 桌宠动画素材与状态机扩充

> **⚠️ 本文 §0–§1 记录的是 2026-11 之前「旧 15 状态素材」的现状，已不再是当前事实。**
> Q 版重做素材已入库并接进状态机（v1.2.0 共 18 状态，v1.3.0 又新增
> `angry`/`attention`/`stretch`/`drag_start` 至 22 状态，且过渡态改为皮肤可选）。
> 当前事实看 [7-状态机接入说明.md](7-状态机接入说明.md)（状态映射表、blink/stretch 取舍、
> 睡眠链、过渡态可选、旧素材保留策略、已知问题）。下面保留旧记录，是因为它解释了
> **为什么**要做重做与重剪，是决策依据而不是现状描述。

> 本目录是「让桌宠更生动」这条线的落地文档与工具说明。
> 只处理「素材 + 动画状态机」，不涉及内核（上下文 / 记忆 / 能力 / 任务）。

## 0. 一句话结论

现有 15 个动作**素材本身能用**（几何一致性极好：角色高 455~460px、脚底 471~474px、中心 x≈180），
问题全在**时长**和**状态机的入口太窄**：

- 一次性动作全部 4~6 秒 → 动作迟钝，像 0.5 倍速慢放
- `blink` 是 6.75 秒（正常人眨眼 0.25 秒），而调度器每 3~8 秒触发一次 → 桌宠几乎一直在眨眼
- **`blink` 那 6.75 秒里绝大部分是"闭眼打瞌睡"**，不是眨眼 —— 这是本节最严重的问题（见 7 号文档 §2）
- `SpriteRenderer` 的多变体随机逻辑写好了，但每个状态只有 1 个 clip → 死代码

> **已被推翻的说法**：本文早期版本写过「15 个状态里模型只能触发 `happy` / `wave`，
> 其余 13 个是死资产」。这句在当时就已经不准 —— `electron/ai/types.ts` 的
> `EMOTION_WHITELIST` 早已是 11 项（`happy/wave/bow/excited/nod/sad/shake/shy/stretch/surprised/thinking`），
> `promptBuilder` 也为这 11 个逐个写了使用语境，`PetStage` 的 `PRIORITY` 覆盖全部 15 个。
> 真正的缺口是「4 个新状态类型层不存在 + blink 素材语义错了 + 拖拽/睡眠没有对应动画」，
> 见 [7-状态机接入说明.md](7-状态机接入说明.md) §0。

### 三个重要更正（比交接提示词里的判断更细）

1. **`blink` 里一共 2 次眨眼（f19、f61），但每次眨眼在源里被画成了约 1.1 秒的慢动作**，
   两次之间是 2.3 秒睁眼站立。所以「6.75s 太长」的真正原因是**单次眨眼本身慢了 4 倍**，
   不是帧抽多了。结论：不能整片提速（会变成抽搐），必须挑帧；而「会眨几次」这件事交给
   调度间隔 + 多变体权重，不要让一条 clip 承担（见 1-素材规格卡的「眨眼节奏」）。
   闭眼帧由逐帧闭眼指数实测得出（先在眼睛带内 ±6px 对齐消掉身体微漂，再算灰度差）：
   f16~f21 与 f58~f62 是全闭平台，各约 0.5s。
2. **存量素材的首/尾帧不可能逐像素对齐锚图**。「标准站姿」在 15 批生成里是 15 个不同的渲染
   （线条/光影/脸型微差），所以 `nod` 的**首帧**与 idle 锚图 SSIM 就只有 0.906。
   这不是姿势错位（几何一致），是**画风批次差**。因此：
   - 质检里「首/尾 vs 锚图 SSIM ≥ 0.95」只能用来约束**新生成**素材（同一模型同一条提示词），
     对存量只能报警告；
   - 想彻底消除切换动作时的细微画风跳，只能重生成（阶段 1）或接受。
3. **不能靠自动差异曲线判语义**。`blink` 的「活动区间」自动检测结果是 f3~f74（等于全片），
   完全没用；闭眼指数也只有「相对高低」可靠（睁眼段因身体旋转残留在 0.62，不是 0）。
   所以裁剪帧号必须**人眼 + 实测曲线互相验证后写进 `avatar-spec.json`**，脚本只负责执行。

## 3. 执行顺序

### 阶段 0 —— 零额度（不花任何生成额度，全部可回滚）

| 步 | 动作 | 动什么文件 | 风险 |
|---|---|---|---|
| 0-1 | `fps` 变速：11 个一次性动作压到 1.2~3.0s | `resources/official-avatars/kirari/frames.json` | 极低（只改数字，git 可退） |
| 0-2 | `blink` 重剪 81→4 帧 + 新增 `blink_double.png` 7 帧变体 | `blink.png`（覆盖，先备份）、新增 `blink_double.png`、`frames.json` | 低（原图在 `.avatar-backup/` 与 git 里） |
| 0-3 | `PetStage.vue` 的 `FALLBACK_DUR` 兜底值同步成新时长 | `src/components/pet/PetStage.vue`（3 行） | 低 |
| 0-4 | `.gitignore` 加 `.avatar-backup/` | `.gitignore`（1 行） | 无 |

> 0-1 与 0-2 已用沙盒副本（复制一份皮肤到临时目录）跑通并通过质检，
> 16 个变体、硬失败 0；命令是 `python scripts/avatar-sheet-tool.py apply --write`。

### 阶段 1 —— 生成管线规格化（要花生成额度）

1. 先做**标准站立锚图**（文生图，一次一张，好坏一眼判）
2. 每个动作 = 首帧锚图 + 尾帧锚图 + 一句动作描述，3~5 秒，720p，16:9
3. 抽帧 12fps → 裁包围盒对齐脚底基线 → 拼表 → 反写 `frames.json`
4. 自动质检（硬失败判废）：绿幕残留 / 空帧 / 身高偏差 / 首尾回锚 SSIM

### 阶段 2 —— 状态机扩充（改代码）

见 [3-动画架构-v2.md](3-动画架构-v2.md) 的「代码改动点清单」。

## 4. 回滚

```bash
# 整目录还原到某次改动之前
python scripts/avatar-sheet-tool.py restore .avatar-backup/20261102-012806

# 或者直接 git 退回（frames.json 走普通 git，PNG 走 LFS）
git checkout -- resources/official-avatars/kirari
```

> 注意：`frames.json` 的 `version` 每次落盘都会 +1。`electron/main.ts` 的
> `mergeBuiltinSkin` 只按版本号决定是否覆盖**元信息**、只补**缺失**的动画声明，
> 不会更新已存在状态的 fps、也不会覆盖同名 PNG。所以**改完素材后，本地必须删掉
> `userData/avatars/kirari` 再启动**，否则会得到一套「旧声明 + 新增状态」的混装皮肤
> （详见 [7-状态机接入说明.md](7-状态机接入说明.md) §5.2）。已安装用户能否拿到更新，
> 需要动 `mergeBuiltinSkin`（见 3 号文档的改动点 H）。

## 5. 未决项（需要拍板）

> 下面 1–3 是**旧素材时代**的问题，Q 版重做后有一部分已经自然消失
> （新素材首尾帧由生成时锚定、单表体积仍大但帧数更分散）。当前仍未决的两项是
> 「24fps 除不尽 60Hz + 一次性动作仍 4–5 秒」与「`mergeBuiltinSkin` 要不要覆盖同名 PNG」，
> 见 [7-状态机接入说明.md](7-状态机接入说明.md) §7 / §5.2。

1. `excited` / `shy` / `stretch` 的尾帧停在「张开手臂」的姿势上，播完切回 idle 会硬跳姿势。
   工具支持 `anchorTail: 3`（追加 3 帧溶解回锚图），但溶解效果要不要得先看实机——默认关。
   （`stretch` 已删除，新素材的 `head_tilt` / `sleep_end` 尾帧本就回到中立站姿。）
2. 素材解码内存：旧素材 15 个状态全量 `new Image()` 约 700 MB。新素材 18 状态合计 1772 帧、
   磁盘 187 MB，解码峰值更高，做**按状态懒加载**的收益比改体积更大（本轮未动）。
3. `mergeBuiltinSkin` 是否要升级成「版本号更高时同时覆盖动画声明与同名 PNG」——本轮实测
   不升级就会得到混装皮肤，但由于会覆盖用户魔改，仍需产品拍板。
