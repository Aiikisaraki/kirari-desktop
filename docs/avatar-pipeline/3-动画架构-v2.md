## 3.1 现状：能力已经写了一部分，但被数据卡住

`SpriteRenderer` 其实**已经支持多变体**了：

```ts
// src/pet/avatar/SpriteRenderer.ts:263
setState(state) {
  const def = this.manifest[state]
  this.clipIndex = def.clips.length > 1 ? Math.floor(Math.random() * def.clips.length) : 0
}
```

但 `frames.json` 里每个状态只有 1 个 clip，所以这段永远是死代码。
真正的瓶颈有两处：

1. **数据**：每状态 1 个变体（阶段 0 的 `blink` 是第一个破例，2 个变体）
2. **入口**：模型只能触发 2 个状态。白名单硬编码在 **4 处**（不是 3 处）：

| 位置 | 内容 |
|---|---|
| `electron/chat-session-service.ts:10` | `export type PetEmotion = "happy" \| "wave"` |
| `electron/chat-session-service.ts:215` | 同步消息时的白名单过滤 |
| `electron/chat-session-service.ts:365` | `pet_response` 到达时的白名单过滤 |
| `electron/adapter/adapter-manager.ts:12, 201` | 协议端同步回聊天框时的白名单 |

渲染层反而没有限制——`src/stores/chat.ts:7` 是
`Exclude<AvatarState, 'idle' | 'blink' | 'sleepy' | 'speak'>`，自动包含全部 11 种情绪。
**所以主进程把 13 个状态全丢了，渲染层根本没机会播。**

## 3.2 单一真源：状态清单只写一次

现状是「状态名在 `src/pet/avatar/types.ts`（渲染层）+ 4 处字符串白名单（主进程）」。
v2 收敛成一份，两个进程都从它读：

```
src/pet/avatar/states.ts        ← 新建：只有常量与类型，不 import 任何渲染器
  export const AVATAR_STATES = ['idle','blink',...] as const
  export type AvatarState = typeof AVATAR_STATES[number]
  export const EMOTION_STATES = AVATAR_STATES.filter(s => !['idle','blink','sleepy','speak'].includes(s))
  export function isEmotionState(v: unknown): v is AvatarState
```

- `src/pet/avatar/types.ts` 改成 `export type { AvatarState } from './states'`（其余不动）
- `electron/chat-session-service.ts` / `adapter-manager.ts` 改成
  `import { isEmotionState } from "../src/pet/avatar/states"`

**为什么能跨进程 import**：这个文件只有字符串常量和类型，没有 DOM/Electron 依赖，
esbuild 打主进程时把它当普通模块内联进去，零副作用。
`electron/*.ts` 目前不在任何 tsconfig 的 `include` 里（只有 vite-plugin-electron 用 esbuild 编译，
不做类型检查），所以这条 import 不会把 DOM 类型拖进主进程。

> 备选方案（如果不想让 electron 依赖 src/）：在 `electron/avatar-states.ts` 复制一份清单，
> 再用一个单元测试断言两边一致。缺点是真源变两份。

## 3.3 `frames.json` v2 结构（向后兼容）

**原则**：所有新字段都是可选的，缺省行为与现在完全一致，
旧扁平格式继续由 `normalizeState` 兼容（不迁移 `public/pet/frames.json`）。

```jsonc
{
  "type": "sprite",
  "name": "Aki Kirari",
  "version": "1.2.0",
  "chatAvatar": "kirari.jpg",

  // 新增（可选）：这套皮肤的播放权重与动作链
  "pool": {
    "weights": { "idle": 80, "wave": 12, "stretch": 6, "blink": 20 },
    "avoidRepeat": 1,          // 连续两次不选同一个状态
    "chains": {
      "greet":  { "steps": ["bow", "wave"], "weight": 4 },
      "nodNod": { "steps": ["nod", "nod"], "weight": 2 }
    }
  },

  "blink": {
    "loop": false,
    "weight": 20,              // 新增（可选）：本状态被抽取的相对权重，0 = 不参与随机
    "clips": [
      { "sheet": "blink.png",        "frameW": 360, "frameH": 480, "frames": 4, "fps": 14, "weight": 3 },
      { "sheet": "blink_double.png", "frameW": 360, "frameH": 480, "frames": 7, "fps": 12, "weight": 1,
        "rate": 1.0 }            // 新增（可选）：播放速率，0.7 = 舒缓，1.3 = 急促
    ]
  },

  // 新增（可选）：派生动作，零素材
  "wave_left": {
    "loop": false,
    "derive": { "from": "wave", "flipX": true }
  },
  "unwind": {
    "loop": false,
    "derive": { "from": "stretch", "reverse": true }
  }
}
```

字段语义：

| 字段 | 位置 | 缺省 | 作用 |
|---|---|---|---|
| `weight` | 状态级 / clip 级 | 1 | 加权随机；0 表示永不自动抽到（只能被显式调用） |
| `rate` | clip 级 | 1.0 | 播放速率倍数 |
| `pool.weights` | 顶层 | 空 | 空闲时自动抽取「下一个自发动作」的权重表，只对这些状态生效 |
| `pool.chains` | 顶层 | 空 | 动作链：按 `steps` 依次播放，用于 `nod+nod` 这类组合 |
| `derive.from` | 状态级 | — | 派生动作，运行时不加载新图，直接复用源 clip 的图 |
| `derive.flipX` / `reverse` | 状态级 | false | 水平翻转 / 倒放 |

`derive` 的价值：**一个 `derive` 条目就多一种表现，磁盘零增长**（见 1-素材规格卡的复用矩阵）。

和现状的区别：现在是 5 个 `setTimeout` 各管一个动作（`scheduleBlink` / `scheduleWave` /

## 3.5 把动作清单交给模型（先设计，不动内核）

现状链路：

```
后端 LLM → pet_response.emotion（枚举）
  → 主进程 4 处白名单过滤（只剩 happy/wave）
  → 渲染层 watch messages → playEmotionThenSpeak(emo)
```

dsh-pet 的做法是**把动作清单本身交给模型**，由它按语境挑一个当场表演，
而不是「模型只输出固定枚举、代码再映射」。改造点只有两个，都在本仓库：

1. **白名单换成清单校验**（3.2 的 `isEmotionState`），主进程不再丢值
2. **把清单喂给后端**：主进程连上后端时发一条 `capabilities` 消息，
   内容形如 `{ emotions: ["happy","nod",...], chains: ["greet","nodNod"] }`，
   由后端拼进系统提示词。这样换皮肤/加动作时**不用改后端提示词**。

   ```jsonc
   // 主进程 → 后端（WS，连上即发一次；皮肤切换后重发）
   { "type": "client_capabilities",
     "emotions": ["bow","excited","nod","sad","shake","shy","stretch","surprised","thinking","happy","wave"],
     "chains": ["greet","nodNod"] }
   ```
   后端的兜底：收到未知 emotion 就按 `happy` 处理（不报错、不影响回复）。

3. **渲染侧的语义**：`playEmotionThenSpeak(emo)` 现在只接一个状态名。
   要支持链式就改成接 `string | string[]`，数组按顺序播、每段间隔 0。

风险：后端在另一个仓库（`kirari-core`）。按发版规范**先推后端、再打前端 tag**。
若不想同时动两个仓库，可以先只做第 1 步（白名单放开），把「清单下发」放到下一轮——
模型仍然输出枚举，但 11 个情绪都能播了，收益已经拿到 90%。

### 关于 E 的额外红线

`SpriteRenderer.hitTest` 与 `draw` 是逐像素点穿链路的最后一环：

- 翻转必须在**绘制**时做（`ctx.save(); ctx.translate(w,0); ctx.scale(-1,1); drawImage(...)`），
  **不能**在 `hitTest` 里镜像坐标——那会让 `cursor - bounds` 算出的 (lx, ly) 与画布像素错位，
  直接导致悬停角色时可拖拽、空白处可点穿的判定反过来。
- 画布尺寸（`canvas.width/height` = `frameW/frameH`）不能因为翻转/倒放而改变。
- 改完在 `[cursor-diag]` 日志里确认：鼠标悬停角色时 `lx ∈ [0, width]`、`ly ∈ [0, height]`，
  且角色实心区能拖动、透明区能点穿。

## 3.7 与 dsh-pet 的机制对照

| 机制 | dsh-pet | 我们（v2） | 落地成本 |
|---|---|---|---|
| 首尾帧约束 | 每段动画首尾都是标准站立 → 任意两段可无缝相接 | 同（锚图 = `idle` 第 0 帧，质检用 SSIM 卡） | 已有素材大部分满足；`excited`/`shy` 需 `anchorTail` |
| 动作池 + 权重 | `animationWeights: {idle:80, turn:0, move:0}` | `pool.weights` + 状态级 `weight` | 中（改动 G） |
| 清单交给模型 | `chatAnimationEnabled` 把动作清单交给模型挑 | `client_capabilities` 下发清单 | 低（只改本仓库侧；后端配合可延后） |
| 睡觉三段接力 | `sleep: [{start, loop, end}]` 每段可多候选 | 现只有 `sleepy` 一个循环冒充全部 | **缺素材**，见 5-动作缺口清单 |
